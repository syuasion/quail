---
title: Logical plans
---

A logical plan describes the operations a query requests and the data they
read. It does not specify GPU batches or attention settings. The SQL parser
and Python builder both use `LogicalPlanBuilder` to construct this plan.
The [optimizer](/docs/architecture/optimizer) then rewrites it before
building a physical plan.

This page describes the plan representation for contributors working on
query syntax, validation, or optimizer rules.

## Plan structure

The plan is a tree. Each node represents an operation, and its children
are the operations that supply its inputs. Data flows from scans toward
the root.

For example, imagine a query that classifies reviews by sentiment and
returns only negative reviews. Its logical plan has these operations:

```text
Result
  Project: r.id, sentiment
    Filter: sentiment IN ('negative')
      SemanticClassify: sentiment
        Scan: reviews as r
```

`SemanticClassify` calls the model and adds a label column. `Filter` tests
that column without calling the model. Keeping the two operations separate
lets the planner reason about their placement and cost.

## The node protocol

All logical nodes implement this protocol:

```python
class LogicalNode(Protocol):
    type_name: ClassVar[str]

    def children(self) -> tuple[LogicalNode, ...]: ...
    def expressions(self) -> tuple[Any, ...]: ...
    def output_schema(self) -> tuple[ColumnRef, ...]: ...
    def validate(self) -> None: ...
    def with_children(self, children) -> LogicalNode: ...
    def with_expressions(self, expressions) -> LogicalNode: ...
    def explain_fields(self) -> dict[str, Any]: ...
```

- `children()` returns the node's inputs.
- `expressions()` returns the expressions attached to the operation.
  A `SemanticFilter` holds `FilterPredicate` objects, which include a
  predicate and a selectivity hint. A `Project` holds output expressions.
- `output_schema()` describes the columns available after the operation.
- `validate()` checks the node's constraints.
- `explain_fields()` supplies fields for the plan's text representation.

Nodes are frozen dataclasses. Rewrites use `with_children()`,
`with_expressions()`, or `dataclasses.replace()` to return new nodes.
`LogicalPlan.walk()` visits children before their parents.

## Node types

| Node | Meaning |
| --- | --- |
| `Scan(provider, alias, column)` | Read document text from a registered table. |
| `SemanticFilter(input, predicates)` | Evaluate model predicates over one table and keep passing rows. |
| `Join(left, right, on)` | Form pairs from two inputs. Optional column equalities, and comparisons beside them, restrict the pairs. Without `on`, it forms every pair. |
| `SemanticJoin(input, predicate, semantics, selectivity, anchor)` | Evaluate a model predicate over the pairs from a `Join`. The semantics are `full`, `exists`, or `anti`. |
| `SemanticClassify(input, call, name)` | Evaluate an `AI.CLASSIFY` call and add the label column `name`. |
| `SemanticExtract(input, call, name)` | Extract one answer field and its character positions from each document. |
| `Filter(input, condition, selectivity)` | Keep rows that satisfy a condition on a label, extracted answer, or answer position. |
| `Apply(input, function, kind, ids, columns, aliases)` | Run a registered Python function on input rows or pairs. |
| `Project(input, columns, structs)` | Select values and assemble extraction structs. |
| `Aggregate(input, keys, aggregates, output, having)` | Group projected rows and compute aggregate values. |
| `Window(input, calls, output)` | Add window values to projected rows, preserving individual rows. |
| `Result(input, limit, order, offset, distinct)` | Set result order, remove duplicates, and apply an offset and limit. This is the root node. |

A query joining three or more tables uses one `SemanticJoin` for each
binary join. A classification may read one document or both documents
of a joined pair. Conditions on labels of joined pairs are unsupported.

A window query places `Window` between `Project` and `Result`. The
projection supplies source columns and AI outputs used by the window.
The window adds values such as a previous row's label or a running
sum. `Result` specifies the final row order and limit.

## Expressions

Expressions describe the values an operator reads, computes, or tests.
A value expression reads a column, accesses a struct field, or applies
a function without calling the model. A `ModelCall` describes an AI
operation.

| Expression | Value |
| --- | --- |
| `ColumnRef(alias, provider, column)` | A reference to a table column. |
| `GetField(input, field)` | A field read from a struct. |
| `ScalarFunction(function, args)` | A value computed for each row, such as text length. |
| `RegularPredicate(expression, comparison, value)` | A condition on a value, such as `length(r.body) < 40`. |
| `ModelCall(prompt, kind, labels, descriptions)` | An AI operation. The kind is `boolean`, `score`, `label`, or `extract`. |
| `Alias(expression, name)` | An expression returned under a specified column name. |
| `WindowCall(function, argument, partition, order, name)` | A window function with its input column, partition keys, order keys, and output name. |

For example, `LENGTH(r.details.body)` reads the `details` column,
selects its `body` field, and computes the text length. Its expression is:

```python
ScalarFunction("length", (
    GetField(ColumnRef("r", "reviews", "details"), "body"),
))
```

Operators use these expressions as follows:

- `Scan.column` specifies the text to tokenize. It can read a source
  column directly or use a value expression, such as a struct field.
- `SemanticFilter` and `SemanticJoin` test a boolean `ModelCall` or a
  `RegularPredicate` that compares an `AI.SCORE` call with a threshold.
- `Filter` tests a label, extracted answer, or answer position with a
  `RegularPredicate`. The condition does not call the model again.
- `Project.columns` specifies the returned values and their names.

`LogicalPlan.operators()` collects the tree's operations for planning.
It includes scans, predicates and joins in written order, Python
functions, score, classification, and extraction calls, and conditions
on their answers.

## Prompt binding

Prompt binding converts a user's template and column references into the
layout the model receives. Quail places document text before the question
so questions about the same document can reuse its KV. KV is the key and
value vectors saved for previously processed tokens.

A template is therefore not treated as a plain string substitution.
For example, `PROMPT('Does {0} praise the acting?', r.body)` identifies
`r.body` as the document, but Quail sends that document before the question.

### Filters

A bound filter prompt contains, in order:

1. A document heading.
2. The document text.
3. The task instruction and question.
4. The answer cue.

For example, for a review with body "The acting was excellent.", this
call:

```sql
PROMPT('Does this review praise the acting? {0}', r.body)
```

uses this layout:

```text
DOCUMENT:
The acting was excellent.
You are performing a data processing task.
Evaluate TRUE or FALSE for the following question:
Does this review praise the acting?
ANSWER:
```

### Joins

The join layout places the anchor document first. The anchor is the side
whose KV remains available while Quail evaluates its partners.

The prompt contains, in order:

1. A heading and the anchor document.
2. The anchor frame, which identifies the anchor and states the question.
3. A heading and the partner document.
4. The answer cue.

The frame is fixed for all partners of an anchor. In the Quail executor,
the first partner heading is also stored with that frame, once per anchor.
Each pair then adds its partner document and answer cue. See
[Join execution](/docs/architecture/execution#joins).

### Classification

A classification prompt includes the document, question, and allowed
categories. Quail prepares both category text and letter choices when
one distinct token is available for each letter. The
[label scoring rule](/docs/architecture/optimizer#label-scoring) chooses
which version to use.

For example, suppose `reviews.body` contains "The acting was excellent."
This call supplies two sentiment categories:

```sql
AI.CLASSIFY(
    PROMPT('What sentiment does this review express? {0}', r.body),
    ARRAY['positive', 'negative'])
```

The version with letter choices has this layout before model chat
formatting is added:

```text
DOCUMENT:
The acting was excellent.

Answer with the letter of exactly one of the categories below for the following question: What sentiment does this review express?

Categories:
- A: positive
- B: negative
ANSWER:
```

The document precedes the question and category list, so another question
can reuse the same document KV. When the model selects A, Quail returns
the category text `positive` in the result column.

### Tokenization

Quail tokenizes documents separately from fixed prompt text. The executor
joins the token sequences without tokenizing the complete text again.
This lets it reuse document tokens across queries. A bound prompt is
text. The planner lowers it once per query with the session's
tokenizer (`quail.planner.prompt_lowering.lower_prompt`), and the
lowered prompt holds the fixed token IDs and counts the cost model and
the executor read.

For a score over one document, the input is:

```python
tokenize(before_document) + tokenize(document) + tokenize(after_document)
```

Separate tokenization can produce different tokens from tokenizing the
complete string. A token can span the boundary between fixed text and
the document, such as a space and the first word. Splitting at that
boundary prevents the combination and can change model scores.

When comparing implementations, use identical token IDs to compare model
execution. A comparison against an implementation that tokenizes the
complete string also measures the effect of tokenization.

## Logical rules

Logical rules rewrite the plan before physical planning. See the
[optimizer](/docs/architecture/optimizer#built-in-rules) for the built-in rules
